# Orhei A11 / Bomba site

## Что изменено

- Услуги загружаются из `public.services`.
- Доставки/заказы загружаются из `public.orders`.
- Статус каждой доставки хранится в `orders.status` и в JSON-поле `orders.payload`.
- Статус «Ожидает» выделяется оранжевой рамкой, «Доставлен» — зелёной.
- Список аккаунтов берётся из `public.profiles`; создание, редактирование и удаление пользователей выполняются через Supabase Edge Function `admin-user`, а не через прямое изменение профилей браузером.
- Не-normalized данные (продажи, кошелёк, архивы, группы, разрешения и логи) пока остаются в `public.app_state.payload`, чтобы не менять их структуру в этом обновлении.
- Резервные копии `backup_20261009_*` в проекте Supabase не удаляются и не меняются.

## Перед публикацией

1. Убедитесь, что `config.js` содержит URL и publishable key именно вашего Supabase-проекта.
2. В Supabase SQL Editor выполните `supabase/migrations/20261009170000_normalize_site_data.sql` один раз. Миграция повторно запускаема: переносит старые записи только в отсутствующие ID и не перезаписывает уже существующие нормализованные строки.
3. Убедитесь, что Edge Function `admin-user` развёрнута и в ней настроены серверные переменные `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY`. Секрет service-role нельзя помещать в `config.js` или HTML.
4. Опубликуйте `index.html`, `config.js`, папку `assets/` и остальные файлы архива на хостинге сайта. Пути к `assets/` должны сохраниться.

## Таблицы

- `public.orders`: `id`, `order_number`, `status`, `created_by`, `created_at`, `updated_at`, `payload`.
- `public.services`: `id`, `service_number`, `created_by`, `created_at`, `updated_at`, `payload`.
- `public.profiles`: авторитетные данные аккаунтов и их разрешений.
- `public.app_state`: остальные разделы сайта, не перенесённые в отдельные таблицы.

Сайт не удаляет старые поля `deliveries` и `services` из существующего JSON автоматически. Новые сохранения перестают записывать туда эти массивы; источником истины для них становятся отдельные таблицы.

## Проверки после публикации

- Войти аккаунтом администратора.
- Открыть «Сервис» и «Доставки», сверить количество записей с Supabase.
- Изменить статус доставки и перезагрузить страницу: статус и цвет рамки должны сохраниться.
- Создать сервис и доставку, проверить появление строк в соответствующих таблицах.
- Через «Пользователи» создать тестовую учётную запись, изменить её и удалить; затем проверить вход тестовым пользователем.
- Проверить продажи, кошелёк, архивы, группы и права — эти разделы остаются в `app_state`.

Перед публикацией рекомендуется скачать отдельную резервную копию проекта Supabase: таблицы `backup_20261009_*` находятся в том же проекте и не заменяют независимый экспорт базы.

### Supabase Preview: remote migration version missing locally

The connected production project already records migration version
`20261009143724` (`create_prechange_backup_20261009`). The corresponding local
migration file is included as a no-op history-alignment entry because the original
pre-change backups contain production-specific data and were created directly in
the database. Do not delete remote migration history or reset the production DB to
resolve this mismatch. The schema migration for normalized orders/services is
`20261009170000_normalize_site_data.sql`.

## Управление пользователями и правами

- В разделе «Пользователи» при создании и редактировании доступны все системные разрешения и пользовательские разрешения из каталога.
- Кнопки «Выбрать все» и «Снять все» помогают быстро выдать или убрать весь набор прав.
- В разделе «Права» можно создавать пользовательские разрешения, менять их название/ключ и удалять пользовательские разрешения. Системные разрешения нельзя удалить из каталога, но их можно снять с любого сотрудника.
- Разделы приложения открываются по соответствующим правам; для просмотра записей других сотрудников предусмотрены отдельные разрешения.
- Удаление учётной записи обрабатывается серверной Edge Function `admin-user`: сначала проверяется профиль, затем удаляется учётная запись Auth; при ошибке удаления Auth профиль восстанавливается. Главного администратора и текущую учётную запись удалить нельзя.
- Пользователю с правом `users.manage` разрешено управлять учётными записями, но он может назначать только те права, которыми обладает сам. Главный администратор может назначать полный набор.
